CLIFF 1.1 - THE SPECIFICATION, COMPRESSED TO ITS RULES

SECTIONS AND ENTRIES ARE SINGLE LINES

  A section line `[group.path]` opens a section; an entry line `<id>` opens an entry.
  Each is a label on one line standing alone, and what it opens runs until the next
  such line or the end of the document. So the last thing in the answer is the last
  field of the last entry, and inside a string `<` and `>` are ordinary characters
  like any other.

The normative grammar, in ABNF (RFC 5234). It is the definition of the format, and
its first production is the whole of what an answer is: one `cliff-file`, from its
version line to its last field. The constraints after the grammar state the rules
a grammar cannot express.

--- GRAMMAR ---
cliff-file            = version-line *header-line *section
version-line         = *WSP %s"CLIFF" SP ( %s"1.0" / %s"1.1" ) *WSP [ terminator ] *WSP LF
header-line          = field-line
section              = section-line *group-metadata-line *entry
section-line         = *WSP "[" group-path "]" *WSP [ terminator ] *WSP LF
group-path           = name *( "." name )
group-metadata-line  = field-line
entry                = entry-line *field-line
entry-line           = *WSP "<" name ">" *WSP [ terminator ] *WSP LF
field-line           = *WSP field *WSP [ terminator ] *WSP LF *continuation-line
continuation-line    = *WSP ( string-value / list ) *WSP [ terminator ] *WSP LF
field                = key *WSP ( "=" / ":" ) *WSP value
value                = string-value / list / integer / name / language-tag
string-value         = string *( *WSP string )
list                 = "[" *WSP [ list-items ] *WSP "]"
list-items           = list-item *( *WSP "," *WSP list-item ) *WSP [ "," ]
list-item            = string / integer / name / language-tag
key                  = name
name                 = name-char *name-char
name-char            = ALPHA / DIGIT / "_" / "-"
tag-name             = %x61-7A *( %x61-7A / DIGIT / "-" )
terminator           = "," / ";"
integer              = 1*DIGIT
language-tag         = ALPHA *( ALPHA / DIGIT / "-" )
string               = double-string / single-string
double-string        = DQUOTE *( double-char / double-escape ) DQUOTE
double-char          = %x20-21 / %x23-5B / %x5D-7E / non-ascii
double-escape        = "\" ( DQUOTE / "\" / "n" / "r" / "t" )
single-string        = SQUOTE *( single-char / single-escape ) SQUOTE
single-char          = %x20-26 / %x28-5B / %x5D-7E / non-ascii
single-escape        = "\" ( SQUOTE / "\" / "n" / "r" / "t" )
non-ascii            = %x80-F4
WSP                  = SP / HTAB
SP                   = %x20
HTAB                 = %x09
DQUOTE               = %x22
SQUOTE               = %x27
LF                   = %x0A
ALPHA                = %x41-5A / %x61-7A
DIGIT                = %x30-39
--- END GRAMMAR ---

SEMANTIC CONSTRAINTS (normative)
Semantic constraints (enforced by validators, not by ABNF):
 * version-line must be the first non-ignored line and must declare 1.0 or
   1.1; any other version is rejected with the supported versions named.
 * Header fields occur before the first section-line; group metadata lines
   occur only before the first entry-line of a section.
 * namespace, clan, source-language, and target-language are all required.
   A layout (folder "<target-language>/<clan>.cliff" or flat
   "<clan>.<target-language>.cliff") that disagrees with the header is a
   WARNING by default in 1.1 (spec 11.3); an implementation MAY offer an
   explicit opt-in mode that reports it as an error.
 * Entry-level: source, type (direct or inherited), and status are
   required; target is optional and required only for status translated /
   reviewed / final (status initial allows a missing target).
 * Section paths and entry ids are unique; duplicate entry ids are a hard
   error (never last-wins). Canonical IDs
   namespace.clan.group-path.entry-id are unique. Case is significant, so
   "Save" and "save" are two different ids.
 * Names are used verbatim: no case folding and no kebab-case rewriting of
   identifiers by a parser (spec 5.5, 10.1). Identifier *style* is a
   recommendation (style/README.md), never a validity rule.
 * Fixed tag vocabularies: type, emotion, status, variant. Tag values are
   tag-name (lowercase kebab-case). Status tags are initial, translated,
   reviewed, final.
 * A field separator is the first "=" or ":" outside a quoted string; the
   entry anchor is the label "<id>" on its own line, and it runs to the next
   entry or section line. "<" and ">" carry no other structural meaning and
   never pair across lines.
 * A line terminator ("," / ";") is recognized only after the value's
   closing quote or bracket, is never significant, and is never emitted by a
   canonical serializer. At most one is permitted per line; a run of them
   (";;", ",,", ", ;") is a syntax error. A ";" or "," inside a quoted string
   is payload, and the optional trailing comma inside a list is the list's
   own production, not a terminator.
 * Every key appears at most once per scope (header, group, entry);
   duplicate keys are validity errors — there are no repeatable fields.
 * Strings containing braces must have balanced braces; the check applies
   to the fully concatenated value after continuation lines are joined.
 * List-typed fields (emotion, dependency, reference) are always written
   as a list, even for a single item; a bare scalar in a list-typed field
   is a validity error. dependency and reference list items are quoted
   path/string values.
 * Continuation lines (string fragments after scalar string fields, bare
   lists after list fields) concatenate verbatim / extend the list in
   order. A blank or comment line ends a continuation; an orphan
   continuation line is a syntax error. Lists themselves never span lines
   and list items never continue across lines.
 * Implementations MUST enforce documented, configurable resource limits in
   both strict and tolerant modes (spec 19): file size, line length, decoded
   string length, group path segment count, list length, and entry count.
 * Tolerant parsing (spec Appendix C) is opt-in, is a superset of this
   grammar, MUST report every repair, and MUST NOT guess the items listed in
   Appendix C.5. Its output MUST be valid under this grammar.
 * The identifier relaxations of C.2.5 apply to an identifier that **begins**
   with a name character (or that uses the quoted form of C.2.4). Angle
   brackets whose content is not such an identifier are not an entry marker:
   the line is rejected under C.5, and a tolerant parser MUST NOT manufacture
   an entry, a group or an identifier out of it, because that would be guessing
   data the document does not contain. The same rule governs the first segment
   of a group path inside "[...]". (Appendix C.2.5 gives the cases.)

ENTRY FIELDS

  target          string

  status          status tag  (required)
  context         string  (inherited)

GROUP FIELDS (the [section.path] line, before the section's first entry)
  context  type  emotion  max-width
  type, emotion, context, max-width may be given on the group instead of on every entry: the entry value overrides the group value, lists do not merge, and at least one of the two provides type. context is joined, group value then entry value with one space. No other entry field is inherited.

ESCAPING (sections 5.7 and 6.2)

  A value is a C-style string literal. Five characters are written with a
  backslash inside it: the double quote (\"), the backslash itself (\\), newline
  (\n), carriage return (\r) and tab (\t) - those five are the whole escape set.
  So a value that contains a quote has \" at that point, however long the value is,
  and the file you were given already spells it that way: the source text and every
  other value come through with their backslashes exactly as written. Chinese,
  Japanese and Korean curly quotes (“ ” 「 」) are ordinary characters and are
  written as they are, with no backslash.

VARIANT: glossary (section 13)

A glossary is the same grammar with variant: glossary: one term per entry, unique
ids, source the term and target its canonical rendering. It is a deliverable of
translation as well as an input, so a term decided while translating is recorded in
one. Section 13.2.2 states the criterion: add the document when the brief asks for
terminology consistency or a naming policy, when a term recurs across entries, or
when a naming judgement would otherwise be re-made differently. The rendering
recorded is the rendering used in the translated file.

Its shape, from section 13.2.1: the header carries variant: glossary, and the clan
of the glossary is the clan it serves with the suffix -terms (settings becomes
settings-terms; a glossary shared by a whole project uses the clan terms). The
entries sit in a section, by convention [terms], one term per entry, each carrying
source (the term), target (the rendering used), type (a term-level tag from the
closed set above), status, and context saying why that rendering was chosen.

Two documents are then one answer. A second document is recognised by its own
version line, so the glossary begins with its own CLIFF 1.1 line placed immediately
after the last field of the translated file, and each document is complete in
itself: the translated file is the first, the glossary is the second.
